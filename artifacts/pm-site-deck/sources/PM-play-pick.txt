 문제 / Problem
 이용 기록이 없는 사용자의 첫 추천에는 입력이 필요했습니다.
 Play Pick은 공연 정보와 사용자 취향을 연결하는 추천 웹 서비스입니다. 가입 직후에는 조회·찜·관람 기록이 없으므로, 첫 추천에 사용할 관심 정보를 별도로 받아야 했습니다.
 공연을 한 장씩 보여주고 호감·비호감·판단 보류를 받는 온보딩 화면을 만들었습니다. 핵심 과제는 각 행동의 의미를 데이터에 다르게 담고, 저장이 끝난 뒤에만 추천으로 이동하는 것이었습니다.

 근거 / Evidence
 세 가지 응답은 저장 규칙이 서로 달랐습니다.
 보고싶어요
 호감 응답으로 공연 ID와 함께 저장 요청에 포함합니다.

 안볼래요
 비호감 응답으로 저장 요청에 포함합니다.

 모르겠어요
 판단 보류로 다음 공연을 보여주되, 비호감으로 저장하거나 완료 개수에 포함하지 않습니다.

 완료 조건
 호감·비호감 응답이 8개 이상일 때 완료할 수 있습니다.

 제품 명세: 호감·비호감 응답 최소 8개

 판단 / Decision
 중립 응답을 제외하고, 저장 성공 뒤에 완료 처리했습니다.
 판단을 보류한 응답을 비선호로 오해하지 않도록 요청 데이터에서 제외했습니다. 호불호가 8개 이상 쌓이면 완료 버튼을 활성화하고, 선택 저장 → 온보딩 완료 → 추천 화면 이동 순서를 지키도록 했습니다.
 01 선택 호감·비호감만 응답 목록에 추가


 02 저장 공연 ID와 응답 값을 서버에 전달


 03 완료 저장이 성공한 뒤 온보딩 완료 처리


 04 이동 추천 화면에서 저장된 취향 사용


 MY ROLE 사용자의 선택 상태, 요청 데이터 변환, 저장·완료 요청 순서와 화면 이동을 프론트엔드에서 연결했습니다.


 실행 / Action
 화면 상태와 서버의 취향 저장 처리를 연결했습니다.
 선택 상태
 현재 공연과 호불호 응답, 유효 응답 개수에 따라 진행 상태와 완료 버튼을 갱신했습니다.

 요청 데이터
 공연 ID와 호감·비호감 값을 서버 요청 형식으로 바꾸고, 중립 응답은 제외했습니다.

 저장 처리
 사용자의 응답을 공연 특성 데이터에 반영해 서버에 취향 정보로 저장하는 처리를 구현했습니다.

 실패 상태
 저장 요청이 실패하면 오류를 보여주고 현재 화면에 머물며, 완료 처리와 추천 이동을 진행하지 않게 했습니다.

 구현 세부 정보
 화면 상태는 Pinia에서 관리했습니다. 보고싶어요는 1.5, 안볼래요는 −1.0으로 전달하고, 서버는 공연 임베딩을 가중 합산·정규화해 사용자 선호 정보로 저장합니다.

 
 역할 분담
 내 담당과 팀원 담당
 내 담당
 팀장으로 화면 설계·프론트엔드, 온보딩 API, 사용자 선호 저장 처리를 맡았습니다.

 팀원 담당
 임경수 팀원이 공연 데이터 수집, 핵심 AI 검색·추천 엔진 개발, 배포 설정을 맡았습니다.

 
 구현 결과
 취향 입력부터 저장·완료·추천 조회까지 연결했습니다.
 호감·비호감·중립 선택, 유효 응답 8개 조건, 취향 저장, 완료 처리와 추천 화면 이동을 연결했습니다. 저장에 실패하면 현재 화면에 머물도록 처리했습니다.

 배움 / Learning
 사용자 행동의 의미와 저장 실패 상태를 함께 다뤘습니다.
 중립 응답을 비선호와 분리하고, 저장에 실패하면 완료 상태로 넘어가지 않게 처리했습니다. 사용자의 선택 의미와 요청 결과를 화면 상태에 함께 반영한 경험이었습니다.
