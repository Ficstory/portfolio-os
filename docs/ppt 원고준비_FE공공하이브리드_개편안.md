# 포트폴리오 PPT 원고 준비 - FE/공공 하이브리드 개편안

## 1. 제작 방향

- 용도: SSAFY 마지막 개발자 컨설턴트 피드백용 포트폴리오 초안
- 포지션: FE/클라이언트 개발자
- 포지셔닝: 정책·공공 문제를 사용자 흐름, 접근성, 상태 관리, API 계약으로 번역해 구현하는 FE/클라이언트 개발자
- 주요 독자: 개발자 컨설턴트, 개발 직무 채용담당자
- 제외 기준: 아직 개발 중인 총괄비서 에이전트 챗 UI는 이번 포트폴리오 본문에서 제외

이번 PPT는 단순한 Android 프로젝트 소개가 아니라, 내가 어떤 사회·생활 문제를 이해했고, 그 문제를 어떤 화면 구조와 상태 흐름, API 연동, 접근성 기준으로 구현했는지 보여주는 개발자 포트폴리오로 만든다.

핵심 메시지는 아래 한 문장으로 유지한다.

```text
공공·생활 문제를 실제 사용 가능한 서비스 흐름으로 구현하는 FE/클라이언트 개발자
```

이번 포트폴리오의 전략은 다음과 같다.

```text
1. 부산이음길로 공공 문제, 접근성, 클라이언트 아키텍처 역량을 먼저 보여준다.
2. 애낌으로 Android 앱 흐름, 권한/분석/알림/구독 관리 구현 역량을 보여준다.
3. Smile Battle로 PM, 서비스 검증, 7인 팀 조율, 사용자 설문 기반 피봇 경험을 보강한다.
4. 정책/사회운동 경험은 전면에 내세우지 않고, 공공 문제 이해와 사용자 요구 분석의 배경으로만 사용한다.
```

## 2. 프로젝트 원고 구조

각 프로젝트는 아래 흐름으로 정리한다.

```text
문제: 어떤 사용자/사회/서비스 문제가 있었나
내 역할: 내가 맡은 개발, 기획, 조율 범위는 무엇인가
해결 방식: 어떤 구조/기술/UX 판단으로 풀었나
결과: 사용자 흐름, 구현 완성도, 협업, 검증 측면에서 무엇이 남았나
배운 점: 다음 프로젝트와 직무에 가져갈 역량은 무엇인가
```

프로젝트별 강조 비중은 아래 기준을 따른다.

| 프로젝트 | 포트폴리오 역할 | 비중 |
|---|---|---:|
| 부산이음길 | 메인 1. 공공 문제 + 접근성 + FE/클라이언트 구조 | 40% |
| 애낌 | 메인 2. Android 앱 구현 + 제품 흐름 + 권한/분석/알림 | 35% |
| Smile Battle | 보강 1. PM/서비스 검증 + 설문 기반 MVP 피봇 | 20% |
| Play Pick | 필요 시 한 줄 보조. Vue/Django 경험 정도만 언급 | 5% |

## 3. 메인 프로젝트 1 - 부산이음길

### 한 줄 소개

부산의 지형과 이동약자의 실제 이동 제약을 반영해, 최단거리가 아니라 실제로 지나갈 수 있는 길을 안내하는 무장애 길찾기 앱을 구현했습니다.

### 문제

일반 길찾기 서비스는 거리와 시간 중심으로 경로를 안내하기 때문에 휠체어 사용자, 저시력자, 고령자, 유아차 사용자가 실제로 이동 가능한 길인지 판단하기 어렵다.

부산은 경사, 계단, 단차, 보도 폭, 엘리베이터, 점자블록, 공사/장애물 같은 변수가 많다. 가까운 길이 실제로는 이동하기 어려운 길이 될 수 있으므로, 지도 서비스는 "빠른 길"보다 "갈 수 있는 길"을 먼저 설명해야 한다.

### 내 역할

FE/Android 개발자로서 사용자 유형별 온보딩, 접근성 지도, 검색/목적지 설정, 경로 안내, 저시력자 전용 흐름, 북마크, 장애물 제보, 마이페이지로 이어지는 핵심 이동 흐름을 화면과 상태 단위로 구현했다.

또한 접근성 정보가 단순 문구로 끝나지 않고 실제 길찾기 흐름에서 판단 근거로 보이도록 화면 구조, 라우트, 상태, API 응답 shape를 맞추는 작업을 수행했다.

### 해결 방식

Jetpack Compose와 Navigation Compose 기반으로 화면을 구성하고, 화면 단위 Route, Screen, ViewModel, Contract 구조를 유지했다.

보행약자와 저시력자의 사용 흐름을 단순 확대 UI로 처리하지 않고, 사용자 유형별 판단 기준이 드러나는 별도 흐름으로 분리했다.

Kakao Map 기반 지도 화면에서는 접근성 시설, 제보 위치, 경로 정보를 시각화하고, 경로 안내에서는 현재 위치, 다음 행동, 경로 세그먼트, 도착 상태가 명확히 보이도록 구성했다.

### 결과

사용자가 로그인/온보딩 이후 목적지를 검색하고, 접근성 정보를 확인한 뒤, 경로 안내를 받고, 도착 후 저장하거나 장애물을 제보하는 end-to-end 흐름을 만들었다.

실제 API와 데이터를 붙이는 과정에서 경로 geometry, segment, 빈 상태, 오류 상태, 긴 장소명, 인증/캐시 흐름을 점검하며 실사용에 가까운 앱 흐름으로 다듬었다.

### 배운 점

공공 문제를 다루는 클라이언트 개발은 화면을 예쁘게 만드는 것보다 사용자가 어떤 기준으로 판단해야 하는지 드러내는 것이 중요하다.

접근성 UX는 일반 화면을 조금 더 크게 만드는 작업이 아니라, 사용자의 이동 방식과 위험 판단 기준에 맞춰 별도의 흐름을 설계하는 작업이라는 점을 배웠다.

### PPT 슬라이드용 압축 문장

```text
부산의 지형과 이동약자의 실제 제약을 반영해, 빠른 길보다 실제로 지나갈 수 있는 길을 안내하는 무장애 길찾기 앱을 구현했습니다.
```

### 강조 키워드

- Jetpack Compose
- Navigation Compose
- 화면 단위 Route/Screen/ViewModel/Contract
- 접근성 UI
- 저시력자 흐름
- Kakao Map SDK
- 경로 안내
- 장애물 제보
- API 연동
- 빈 상태/오류 상태 대응

## 4. 메인 프로젝트 2 - 애낌

### 한 줄 소개

구독 현황을 보여주는 앱을 넘어, 결제 내역과 사용 흐름을 바탕으로 사용자가 절감 행동까지 이어갈 수 있는 Android 구독 관리 경험을 구현했습니다.

### 문제

구독 서비스가 늘어나면서 사용자는 결제일, 사용량, 해지 시점, 대체 혜택을 한눈에 관리하기 어렵다. 단순히 "무엇을 구독 중인지" 보여주는 것만으로는 불필요한 지출을 줄이는 행동으로 이어지기 어렵다.

### 내 역할

팀장 겸 FE/Android 개발자로서 화면 구조, API 연동 범위, 주요 상태 흐름, 구현 우선순위를 정리했다.

온보딩, 권한/분석, 구독 확인, 대시보드, 인사이트, 체크인, 해지 가이드, 프로모션 추천, 알림함, 마이페이지로 이어지는 흐름이 끊기지 않도록 앱 구조와 화면 상태를 맞췄다.

### 해결 방식

Jetpack Compose 기반으로 구독 분석 이후 사용자가 "현황 파악 → 사용량 확인 → 저사용 구독 체크인 → 해지 가이드 또는 대체 혜택 탐색"으로 이동할 수 있는 흐름을 구성했다.

월 구독 총액, 절감 가능 금액, 검토 필요 항목, 체크인 CTA, 추천 혜택을 대시보드에 나누어 배치했다.

FCM 토큰 동기화, 푸시 딥링크, UsageStats 권한, 소셜 로그인, 내부 약관 화면, 알림 설정처럼 앱 운영에 필요한 주변 흐름도 함께 정리했다.

### 결과

구독을 조회하는 화면에서 끝나지 않고, 사용량 확인, 저사용 구독 체크인, 해지 가이드, 대체 프로모션 탐색까지 이어지는 절감 행동 중심의 앱 경험을 만들었다.

프로젝트 문서와 구현 기준을 맞추며, 요구사항정의서와 화면명세서가 실제 앱 흐름을 설명하는 기준 문서가 되도록 정리했다.

### 배운 점

좋은 클라이언트 개발자는 화면을 구현하는 것에서 끝나지 않고, 사용자가 어떤 판단을 해야 하는지까지 구조화해야 한다.

PM과 구현을 병행하면서 기획 문서, API 계약, 화면 상태, 예외 흐름, QA가 서로 어긋나지 않도록 관리하는 역량이 중요하다는 것을 체감했다.

### PPT 슬라이드용 압축 문장

```text
구독 현황 조회에서 끝나지 않고, 사용량 확인과 체크인, 해지 가이드, 대체 혜택 탐색까지 이어지는 절감 행동 중심 앱 경험을 구현했습니다.
```

### 강조 키워드

- Android 개발
- Jetpack Compose
- 팀장 / PM 병행
- 구독 분석 흐름
- UsageStats 권한
- 대시보드 정보 구조
- 체크인 / 해지 가이드
- 프로모션 추천
- FCM / 딥링크
- 요구사항정의서 / 화면명세서 정합성

## 5. 보강 프로젝트 - Smile Battle

### 한 줄 소개

실시간 화상 웃음참기 대결 서비스를 7인 팀에서 PM으로 리드하며, 168명 설문 결과를 바탕으로 MVP를 재정립했습니다.

### 문제

초기 아이디어는 웃음 감지 AI와 WebRTC를 결합한 실시간 대결 서비스였지만, 컨설턴트 피드백에서 "토이 프로젝트처럼 보일 수 있다"는 우려가 있었다.

기술적으로 재미있는 아이디어만으로는 실제 사용자가 왜 참여해야 하는지, 어떤 불편을 느끼는지, 어떤 위험을 피해야 하는지 설명하기 어려웠다.

### 내 역할

PM 겸 프론트엔드 개발자로서 팀의 시장조사와 아이디어를 통합하고, 컨설턴트 피드백을 액션 아이템으로 바꿨다.

설문조사를 설계·배포하고 168개 응답을 분석해, 얼굴 노출 부담과 매칭 방식에 대한 사용자 우려를 확인했다.

### 해결 방식

설문 결과를 바탕으로 MVP를 랜덤 매칭 중심에서 친구/지인 매칭을 함께 고려하는 방향으로 조정했다.

캡처/녹화 방지, 악성 유저 관리, OpenVidu 기반 화상 연결, 실시간 웃음 감지 응답 속도 같은 기술·서비스 리스크를 기능명세서의 우선순위에 반영했다.

### 결과

아이디어를 고집하지 않고, 사용자 응답과 컨설턴트 피드백을 근거로 서비스 방향을 빠르게 피봇했다.

회의록, 시장조사, 설문 결과 분석, 기획서, 기능명세서를 남겨 팀의 의사결정 기준을 문서화했다.

### 배운 점

PM 역할은 아이디어를 많이 내는 사람이 아니라, 불확실한 상황에서 팀이 같은 기준으로 판단할 수 있게 만드는 사람이라는 점을 배웠다.

FE/클라이언트 개발자로서도 화면 구현 전에 사용자 검증과 서비스 리스크를 확인해야 구현 우선순위가 흔들리지 않는다는 점을 체감했다.

### PPT 슬라이드용 압축 문장

```text
7인 팀 PM으로 컨설턴트 피드백을 168명 설문 검증으로 연결하고, 얼굴 노출 부담이라는 사용자 리스크를 반영해 MVP를 재정립했습니다.
```

### 강조 키워드

- PM
- 7인 팀 조율
- 168명 설문
- MVP 피봇
- WebRTC
- OpenVidu
- AI 웃음 감지
- 기능명세서
- 회의록 / 시장조사
- 컨설턴트 피드백 반영

## 6. 전체 포트폴리오에서 줄일 내용

이번 PPT에서는 아래 내용을 줄인다.

- 총괄비서 에이전트 챗 UI: 아직 개발 중이므로 본문 제외
- 사회운동 경험의 장문 서사: 개발 포트폴리오에서는 공공 문제 이해의 배경으로만 짧게 언급
- 정책지원관용 조례·행감·예산 서사: 별도 직무용 포트폴리오에서 사용
- Play Pick의 FE 구현 과장: 본인 역할이 총괄/백엔드/API 쪽으로 기록되어 있으므로 보조 이력 정도로만 언급
- “혁신”, “완벽”, “사용자 중심” 같은 추상 문구: 구현 근거가 있는 문장으로 대체

## 7. PPT 슬라이드별 주요 내용 및 AI 제작 프롬프트

### 공통 디자인 시스템

아래 디자인 시스템은 모든 페이지 프롬프트에 동일하게 적용한다. 단순히 예쁜 PPT가 아니라, 개발자 컨설턴트가 구현 범위와 포지셔닝을 빠르게 판단할 수 있는 기술 포트폴리오 문서로 만든다.

- 문서 성격: SSAFY 마지막 개발자 컨설턴트 피드백용 FE/클라이언트 개발자 포트폴리오
- 전체 톤: 차분한 technical product portfolio, 공공 문제를 다루지만 캠페인 자료처럼 보이지 않게 구성
- 디자인 기준: Android 앱 캡처는 Material Design 3의 모바일 UI 원칙을 따르고, 전체 문서는 Carbon/Atlassian/Primer 계열의 정보 밀도와 개발자 문서형 레이아웃을 참고한다.
- 화면 비율: 16:9 와이드 PPT
- 색상: 배경은 화이트 또는 아주 옅은 쿨그레이, 본문은 차콜/블랙, 보조 텍스트는 그레이, 포인트 컬러는 블루와 그린을 제한적으로 사용한다. 사회/공공 주제라고 해서 초록색만 과하게 쓰지 않는다.
