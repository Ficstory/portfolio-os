# Acctual 레퍼런스 기반 PM 포트폴리오 적용 계획

작성일: 2026-06-09

대상 레퍼런스: https://www.acctual.com/

적용 대상: 이 포트폴리오 사이트의 **PM 포트폴리오 트랙(`/pm`)만**

## 1. 목표

Acctual 사이트의 형식은 결제/인보이스 SaaS 랜딩 페이지다. 이 문서는 Acctual의 시각 요소를 복제하기 위한 문서가 아니라, Acctual이 사용하는 **전환형 정보 설계와 설득 구조**를 PM 포트폴리오에 맞게 번역하기 위한 실행 계획이다.

이번 적용의 핵심 목표는 다음과 같다.

- `/pm` 경로를 PM 직무 지원자용 포트폴리오 랜딩으로 강화한다.
- 공공 디지털 서비스, 정책지원관, 국회보좌관 트랙은 변경하지 않는다.
- Acctual의 "문제 제기 -> 해결 방식 -> 증거 -> 비교 -> FAQ -> CTA" 흐름을 PM 포트폴리오에 맞게 변환한다.
- PM 채용자가 확인하고 싶은 역량, 즉 문제 정의, 요구사항 정리, 우선순위 판단, 산출물, 협업, 실행 결과를 한 페이지에서 빠르게 검증할 수 있게 한다.
- 기존 포트폴리오의 OS/직무 트랙 구조는 유지하되, PM 트랙만 독립적인 설득력이 생기도록 만든다.

## 2. 현재 코드 구조 기준 적용 범위

현재 `/pm` 페이지는 다음 구조로 동작한다.

- `src/app/pm/page.tsx`
  - `TrackLandingPage trackId="pm"`을 렌더링한다.
- `src/components/tracks/TrackLandingPage.tsx`
  - 모든 직무 트랙이 공유하는 랜딩 컴포넌트다.
- `src/components/tracks/trackLandingModel.ts`
  - 트랙별 카피, 증거, CTA, 케이스 섹션 문구를 제공한다.
- `src/lib/portfolioTrack.ts`
  - `pm`, `publicDigital`, `policy`, `assembly` 등 직무 트랙 프로필과 정렬 순서를 정의한다.

따라서 PM 포트폴리오만 바꾸려면 공용 컴포넌트를 전역 수정하는 방식은 위험하다. 권장 구현 방식은 다음 중 하나다.

### 권장 방식 A: PM 전용 랜딩 컴포넌트 생성

가장 안전한 방식이다.

수정 범위:

- `src/app/pm/page.tsx`
  - 기존 `TrackLandingPage trackId="pm"` 대신 PM 전용 컴포넌트를 렌더링한다.
- `src/components/tracks/pm/PmLandingPage.tsx`
  - 새로 생성한다.
- `src/components/tracks/pm/pmLandingContent.ts`
  - PM 전용 섹션 데이터, FAQ, 비교표, 케이스 요약을 별도 관리한다.
- 필요 시 `src/components/tracks/pm/*` 하위에 PM 전용 작은 컴포넌트를 만든다.

장점:

- `/public-digital`, `/policy`, `/assembly`에 영향이 없다.
- Acctual식 구조를 PM에 맞게 자유롭게 재구성할 수 있다.
- 공용 `TrackLandingPage`의 기존 안정성을 유지할 수 있다.

단점:

- PM 페이지용 컴포넌트가 새로 생기므로 약간의 중복이 생길 수 있다.

결론:

- 이번 작업에는 방식 A를 우선 추천한다.

### 대안 방식 B: 공용 컴포넌트 내부에서 PM 분기 추가

가능은 하지만 주의가 필요하다.

수정 범위:

- `TrackLandingPage.tsx` 내부에서 `trackId === "pm"`일 때만 PM 전용 섹션을 추가한다.
- 기존 공용 섹션은 유지한다.

주의:

- 공용 컴포넌트의 레이아웃, 여백, 배경, 네비게이션을 바꾸면 다른 직무 트랙도 같이 바뀐다.
- 반드시 `model.track.id === "pm"` 조건 안에서만 PM 전용 변경을 넣어야 한다.

결론:

- 유지보수 편의는 있지만, 이번 목적에는 방식 A보다 덜 안전하다.

## 3. 절대 변경하지 말아야 할 범위

이번 작업은 PM 포트폴리오만 바꾸는 작업이다. 다음은 기본적으로 수정하지 않는다.

- `src/app/public-digital/page.tsx`
- `src/app/policy/page.tsx`
- `src/app/assembly/page.tsx`
- `src/components/tracks/TrackLandingPage.tsx`의 공통 레이아웃
- `src/components/tracks/TrackHero.tsx`의 전역 Hero 구조
- `src/components/tracks/TrackCaseSection.tsx`의 전역 케이스 섹션 구조
- `src/components/tracks/TrackProofPanel.tsx`의 전역 증거 패널 구조
- `src/lib/portfolioTrack.ts`의 `publicDigital`, `policy`, `assembly` 트랙 데이터

예외:

- 타입 추가, import 정리, PM 전용 분기를 위해 최소 수정이 필요할 때만 변경한다.
- 변경하더라도 다른 트랙의 렌더링 결과가 달라지지 않아야 한다.

## 4. Acctual 사이트 구현 방식 분석

Acctual은 일반적인 회사 소개형 페이지가 아니라, 명확한 전환 목표를 가진 SaaS 랜딩 페이지다.

공개 페이지 기준 핵심 구조는 다음과 같다.

1. 짧은 Hero
   - "Get paid on time"처럼 한 문장으로 핵심 문제 해결을 제시한다.
   - 첫 화면에서 사용자의 문제와 제품의 이점을 동시에 보여준다.

2. 즉시 보이는 신뢰 지표
   - "Used by 5,000+ businesses worldwide"처럼 신뢰를 빠르게 만든다.
   - 숫자, 수수료, 결제 방식 같은 구체 정보를 첫 화면 가까이에 둔다.

3. 타깃 사용자 분류
   - Freelancer, Agency, Consultant, Contractor 등 사용자군을 나눈다.
   - 방문자가 "내 상황에도 맞는가?"를 빠르게 판단하게 한다.

4. 기존 대안의 문제 정의
   - 회계 플랫폼을 Slow, Expensive, Confusing으로 규정한다.
   - 제품을 설명하기 전에 기존 문제를 먼저 선명하게 만든다.

5. 해결책 요약
   - "Same day payments. No subscription."처럼 해결책을 압축한다.
   - 낮은 수수료, 다양한 결제수단, 당일 정산, 회계 연동 등 핵심 효용을 리스트화한다.

6. 기능별 상세 섹션
   - 기능 제목, 짧은 설명, 제품 이미지, 고객 후기, CTA가 반복된다.
   - 각 기능은 사용자의 특정 고통을 해결하는 증거로 제시된다.

7. 비교표
   - Pricing 페이지에서 경쟁 서비스와 수수료, 정산 속도, 결제수단 등을 비교한다.
   - 장점을 주장하지 않고 표로 검증하게 만든다.

8. FAQ
   - 무료 여부, 경쟁 서비스 비교, 결제 링크 작동 방식, 국제 결제, 브랜딩 가능 여부 등을 설명한다.
   - 전환 직전의 불안을 제거한다.

9. 반복 CTA
   - Hero, 중간 기능 섹션, 하단에서 CTA를 반복한다.
   - 사용자가 확신하는 순간 바로 행동하게 만든다.

## 5. PM 포트폴리오로 번역할 핵심 원칙

Acctual의 구조를 PM 포트폴리오에 적용할 때의 번역 원칙은 다음과 같다.

| Acctual 요소 | PM 포트폴리오 적용 |
| --- | --- |
| Get paid on time | 어떤 문제를 푸는 PM인지 한 문장으로 제시 |
| Used by 5,000+ businesses | 프로젝트, 산출물, 협업, 출시 경험 등 검증 가능한 증거 |
| Who is this for? | 내가 잘 해결하는 제품 문제 유형 |
| Slow / Expensive / Confusing | Fragmented / Ambiguous / Costly 같은 문제 프레이밍 |
| Same day payments / No subscription | 나의 PM 운영 원칙 |
| 기능별 제품 이미지 | PM 산출물 카드, 케이스 스터디 카드 |
| Pricing 비교표 | Before / After 또는 대안 비교표 |
| 고객 후기 | 실제 성과, 문서 증거, 협업 범위 |
| FAQ | 채용자가 가질 의문에 대한 선제 답변 |
| Sign up CTA | 대표 프로젝트 보기, 이력서, 연락하기 |

중요한 점은 Acctual의 시각 스타일을 베끼는 것이 아니다. PM 포트폴리오에서는 제품 판매보다 **나의 판단 능력과 실행 증거**가 먼저 보여야 한다.

## 6. PM 트랙의 새 페이지 콘셉트

추천 포지셔닝 문장:

> 복잡한 사용자 흐름, 정책/운영 제약, 개발 현실을 함께 보고 실행 가능한 제품 전략으로 바꾸는 PM

이 문장은 PM과 공공 디지털 서비스 기획자의 접점을 모두 살리되, 최종 초점은 PM에 둔다.

페이지의 톤은 다음과 같아야 한다.

- 과장된 스타트업식 성장 문구보다 실무적이고 검증 가능한 문장
- "저는 열정적입니다"보다 "이 문제를 이렇게 정의했고, 이렇게 실행했습니다"
- "기능을 만들었다"보다 "왜 이 기능이 필요했고, 어떤 범위로 줄였고, 무엇을 확인했습니다"
- 개발자 포트폴리오가 아니라 PM 포트폴리오이므로 코드보다 요구사항, 흐름, 협업, 의사결정 로그를 강조

## 7. 추천 페이지 구조

PM 전용 페이지는 아래 순서로 구성한다.

## 8. 섹션별 상세 설계

### 8.1 Header

목적:

- PM 포트폴리오 페이지 안에서 주요 섹션으로 이동할 수 있게 한다.
- 기존 사이트 전체 내비게이션과 충돌하지 않게 한다.

구성:

- 좌측: `LEE JAEHO / PM Portfolio`
- 우측 앵커:
  - `Work`
  - `Process`
  - `Artifacts`
  - `FAQ`
  - `Contact`
- CTA:
  - `Resume`

주의:

- 다른 직무 트랙 링크를 제거할 필요는 없다.
- 다만 PM 페이지에서는 PM 작업에 집중되도록 섹션 내 앵커를 우선 배치한다.

### 8.2 Hero

목적:

- 첫 화면에서 PM 포지셔닝과 증거를 동시에 보여준다.

추천 구성:

- Eyebrow: `Junior PM / Service Planning`
- H1: `복잡한 서비스 문제를 실행 가능한 제품 전략으로 바꾸는 PM`
- Subcopy:
  - `사용자 흐름, 정책/운영 제약, 개발 현실을 함께 보고 요구사항, MVP 범위, 협업 기준으로 정리합니다.`
- CTA:
  - `대표 프로젝트 보기`
  - `PM 산출물 보기`
  - `이력서 보기`
- Hero 오른쪽 시각 요소:
  - Acctual의 인보이스 카드 스택처럼 PM 산출물 카드 스택을 만든다.
  - 예시 카드:
    - `Requirement Brief`
    - `User Flow`
    - `MVP Scope`
    - `Decision Log`
    - `Launch Checklist`

구현 포인트:

- 실제 문서 이미지가 없으면 카드형 UI로 표현한다.
- 카드 안에는 긴 설명을 넣지 않는다.
- 각 카드는 PM 산출물의 성격을 한눈에 보여주는 제목, 짧은 메타, 2~3개 항목으로 구성한다.

### 8.3 Proof Metrics

목적:

- 추상적인 자기소개를 검증 가능한 증거로 바꾼다.

카드 예시:

- `4` 대표 프로젝트 정리
- `6` 정책/공공 문서형 경력 근거
- `PRD / IA / Wireframe / QA` 산출물 경험
- `기획 + 구현 이해` PM-개발 협업 경험

주의:

- 실제로 검증할 수 없는 성과 수치를 만들지 않는다.
- 정량 성과가 부족하면 "산출물 수", "경험 범위", "협업 범위" 중심으로 표현한다.

### 8.4 PM Fit Segments

Acctual의 "Who is this for?"를 PM 포트폴리오에 맞게 변환한다.

섹션 제목 예시:

- `제가 강점을 보이는 제품 문제`
- `Where I Create PM Impact`

카드 구성:

1. 복잡한 신청/접수 흐름
   - 사용자가 어디서 멈추는지 보고 단계, 안내, 상태를 재정리한다.

2. 정책/운영 제약이 있는 서비스
   - 제도, 운영, 접근성, 민원 맥락을 요구사항으로 번역한다.

3. 내부 운영 도구
   - 반복 확인, 수작업, 부서 간 전달을 줄이는 관리자 흐름을 설계한다.

4. MVP 범위 조율
   - 요청 목록을 검증 가능한 최소 기능과 후순위 항목으로 나눈다.

5. 개발 협업 기준 정리
   - 화면, 상태값, 예외 케이스, API 연동 기준을 문서화한다.

### 8.5 Problem Framing

Acctual의 Slow / Expensive / Confusing을 PM 문제 프레이밍으로 바꾼다.

추천 3분류:

1. Fragmented
   - 사용자 흐름, 관리자 흐름, 정책 조건이 따로 움직인다.
   - PM 적용: 전체 서비스 흐름과 상태 전이를 한 문서에 정렬한다.

2. Ambiguous
   - 요구사항은 많지만 성공 기준과 우선순위가 불명확하다.
   - PM 적용: 문제, 사용자, 제약, 성공 기준을 분리해서 정의한다.

3. Costly
   - 반복 문의, 재작업, 수작업 확인이 운영 비용을 키운다.
   - PM 적용: 자동화 가능 지점, 안내 개선, 관리 화면 요구사항을 정의한다.

이 섹션은 PM 포트폴리오에서 매우 중요하다. 채용자는 이 섹션을 통해 지원자가 단순 실행자가 아니라 문제를 구조화하는 사람인지 확인한다.

### 8.6 PM Operating System

목적:

- "나는 PM으로 어떻게 일하는가"를 프로세스가 아니라 판단 방식으로 보여준다.

추천 단계:

1. 문제 정의
   - 사용자 불편, 운영 병목, 조직 목표를 분리한다.

2. 흐름 설계
   - 사용자 플로우와 관리자/운영자 플로우를 함께 그린다.

3. 범위 결정
   - 임팩트, 구현 난이도, 리스크, 검증 가능성을 기준으로 MVP 범위를 정한다.

4. 요구사항 문서화
   - 화면, 상태값, 정책 조건, 예외 케이스, API 연결 지점을 명확히 쓴다.

5. 협업 정렬
   - 디자이너, 개발자, 운영/정책 담당자가 같은 기준으로 판단하게 만든다.

6. 출시 후 검증
   - 피드백, QA 이슈, 사용 로그, 운영 이슈를 다시 개선 과제로 전환한다.

### 8.7 Featured PM Case Studies

목적:

- 대표 프로젝트를 PM 관점으로 재해석한다.

추천 표시 개수:

- 3개

추천 카드 구조:

- 프로젝트명
- 한 줄 요약
- 문제
- 나의 역할
- 주요 PM 판단
- 산출물
- 결과 또는 배운 점
- 상세 보기 CTA

추천 프로젝트 우선순위:

1. `AEKKIM`
   - 요구사항 정의, 화면 명세, MVP 범위 조율을 가장 강하게 보여줄 수 있는 PM형 프로젝트

2. `부산 이음길`
   - 공공 디지털 서비스/사용자 흐름/접근성 맥락을 보여줄 수 있는 프로젝트

3. `Play Pick` 또는 `Smile Game`
   - 사용자 피드백, MVP 조정, 화면 흐름 개선 경험이 있는 프로젝트를 선택

주의:

- 기술 스택 설명이 중심이 되면 PM 포트폴리오의 설득력이 떨어진다.
- 각 프로젝트마다 "내가 어떤 결정을 했는가"를 반드시 포함한다.

### 8.8 Before / After Impact

Acctual Pricing의 비교표를 PM용으로 변환한다.

추천 표 구조:

| 기준 | 기존 상태 | PM으로 정리한 방식 | 기대/확인된 효과 |
| --- | --- | --- | --- |
| 사용자 흐름 | 단계와 안내가 분산됨 | 핵심 행동 중심으로 재배치 | 이해 부담 감소 |

| 협업 | 구두 합의와 개별 해석 | 문서 기준과 결정 로그 | 재작업 감소 |
| 운영 | 수작업 확인 반복 | 상태값, 알림, 관리 기준 정의 | 운영 부담 감소 |

### 8.9 Product Artifacts

목적:

- PM 역량을 말이 아니라 산출물 유형으로 보여준다.

카드 예시:

- Requirement Brief
- IA / User Flow
- Screen Specification
- MVP Scope
- Backlog Priority
- API Alignment Notes
- QA Scenario
- Launch Review

각 카드 구성:

- 제목
- 어떤 상황에서 쓰는 문서인지
- 포함하는 항목 2~3개
- 관련 프로젝트

주의:

- 실제 원문 문서가 공개 불가능하면 "비공개 산출물 유형"으로 표현한다.
- 허위로 실제 문서 링크가 있는 것처럼 만들지 않는다.

### 8.10 Collaboration Model

목적:

- PM이 혼자 문서 쓰는 사람이 아니라 여러 직군의 판단 기준을 정렬하는 사람임을 보여준다.

구성:

1. Designer
   - 문제 정의, 화면 의도, 정보 우선순위 정렬

2. Engineer
   - 상태값, 예외 케이스, API 조건, 구현 범위 정리

3. Policy / Operation
   - 제도 조건, 실제 처리 절차, 민원 흐름 확인

4. Stakeholder
   - 목표, 일정, 범위, 출시 기준 합의

### 8.11 Public-Service Domain Bridge

목적:

- PM 포트폴리오이지만 공공 디지털 서비스 기획자로도 일부 확장 가능한 강점을 남긴다.

섹션 제목 예시:

- `공공 맥락은 제 PM 역량의 차별점입니다`
- `Public-service context, product execution mindset`

내용:

- 공공 자료와 정책 맥락을 읽는 경험이 있다.
- 사용자 불편뿐 아니라 제도, 접근성, 운영 지속성을 함께 본다.
- 민원, VOC, 정책 문서를 제품 개선 근거로 바꿀 수 있다.
- 빠른 출시만이 아니라 신뢰성, 설명 가능성, 유지 운영을 고려한다.

주의:

- 이 섹션이 PM보다 공공 디지털 서비스 기획자 페이지처럼 보이면 안 된다.
- 공공 맥락은 PM의 차별화 요소로 배치한다.

### 8.12 FAQ

Acctual의 FAQ는 전환 직전 불안을 줄인다. PM 포트폴리오에서도 채용자의 의문을 먼저 해소해야 한다.

추천 FAQ:

1. 개발자가 아닌데 개발팀과 어떻게 협업하나요?
   - 화면, 상태값, 예외 케이스, API 연결 기준을 문서화해 해석 차이를 줄인다고 답한다.

2. 정량 지표가 부족한 프로젝트는 어떻게 설명하나요?
   - 지표를 과장하지 않고 문제 정의, 산출물, 의사결정, 검증 방식으로 설명한다고 답한다.

3. 공공/정책 경험은 PM과 어떻게 연결되나요?
   - 복잡한 자료를 구조화하고 이해관계자 제약을 요구사항으로 번역한 경험이라고 답한다.

4. 본인이 직접 한 일과 팀 성과는 어떻게 구분하나요?
   - 각 케이스에서 역할, 산출물, 의사결정 기여를 분리해 표기한다고 답한다.

5. 어떤 PM 역할에 가장 잘 맞나요?
   - Junior PM, APM, 서비스 기획, 공공/운영형 디지털 서비스, 내부 도구 기획에 적합하다고 답한다.

## 9. 디자인 방향

Acctual에서 참고할 디자인 패턴:

- 넓은 여백
- 강한 단문 헤드라인
- 카드형 증거
- 반복 CTA
- 제품 UI처럼 보이는 시각적 산출물
- 비교표
- FAQ
- 타깃/문제 유형 카드

PM 포트폴리오에 맞게 조정할 점:

- 과도한 SaaS 홍보 느낌을 줄인다.
- 카드와 표는 예쁘기보다 검증 가능하게 만든다.
- PM 산출물은 실제 문서처럼 신뢰감 있게 표현한다.
- 모든 섹션은 "나는 어떤 PM인가"라는 하나의 메시지로 연결한다.

색상/스타일 방향:

- 기존 사이트의 `slate`, `sky`, `white` 계열을 유지하는 것이 안전하다.
- PM 페이지에만 약간의 강조색을 추가할 수 있지만, 전체 사이트 테마를 바꾸지 않는다.
- 카드 radius는 기존 규칙과 맞춰 8px 이하 또는 현재 컴포넌트 스타일을 따른다.

반응형 기준:

- 모바일에서 Hero 카드 스택은 텍스트 아래로 내려간다.
- 비교표는 모바일에서 가로 스크롤 또는 카드형 행으로 변환한다.
- 카드 안 긴 한국어 문장은 줄바꿈, `overflow-wrap`, `min-width: 0`을 고려한다.
- 버튼 텍스트가 넘치지 않게 `flex-wrap` 또는 `w-full sm:w-auto`를 적용한다.

## 14. 최종 판단

Acctual 레퍼런스는 PM 포트폴리오에 적용할 가치가 높다. 다만 그대로 적용하면 SaaS 제품 판매 페이지처럼 보일 수 있으므로, 다음 원칙을 지켜야 한다.

- 제품 기능 소개가 아니라 PM 판단과 산출물 소개로 바꾼다.
- 고객 전환 CTA가 아니라 채용자 검증 CTA로 바꾼다.
- 경쟁 서비스 비교표가 아니라 Before / After, 대안 비교, 의사결정 근거표로 바꾼다.
- 후기 대신 실제 산출물, 역할, 협업 범위, 검증 가능한 결과를 둔다.
- 전체 포트폴리오가 아니라 `/pm` 트랙만 바꾼다.

이 방식으로 적용하면 Acctual의 장점인 명확한 문제 정의, 반복 가능한 설득 흐름, 강한 시각적 증거 구조를 살리면서도 PM 포트폴리오에 필요한 실무 검증력을 확보할 수 있다.
